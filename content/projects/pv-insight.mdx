## 프로젝트 개요

태양광 발전소는 넓은 구역에 많은 패널이 설치되어 있어 모든 패널을 정기적으로 점검하려면 많은 시간과 인력이 필요합니다. 이미지 분석으로 이상 가능성이 높은 구역을 먼저 선별해 관리자의 점검 우선순위와 후속 조치 판단을 지원하는 것을 목표로 했습니다.

RGB와 열화상 이미지는 확인할 수 있는 이상 유형이 달라 각각 별도의 모델로 분석합니다. **RGB 이미지에서는 파손, 식생 침범, 오염, 패널 누락, 음영의 5개 외관 이상을 분석하고 열화상 이미지에서는 국부 과열, 다이오드 동작 이상, 패널 연결 구간 고장의 3개 유형을 확인**합니다.

분석 결과는 bounding box와 mask로 시각화하고 이상 유형에 따라 청소, 재촬영, 현장 점검, 교체 검토 등의 유지보수 조치 후보를 제공합니다. 이미지 등록부터 비동기 분석, 결과 저장과 조회까지 이어지는 서비스 흐름으로 구성했습니다.

## 담당 역할

**RGB 세그멘테이션 모델링** 

- YOLOv26s-seg 기반 RGB 5개 클래스 모델의 입력 해상도, 라벨 정제, fine-tuning 조건을 비교해 작은 결함 탐지 성능 개선
- 상위 성능을 보인 두 모델을 fine-tuning하고, validation 기준으로 checkpoint별 전체 및 클래스별 성능 비교

**ONNX 추론 및 FastAPI AI Worker 구현**

- PyTorch 모델의 raw FP32 ONNX 변환·정합성 검증과 ONNX Runtime 기반 instance mask 후처리 구현
- SQS 메시지 수신·검증, 분석 Job 조회·상태 전환과 처리 결과별 메시지 삭제를 수행하는 FastAPI AI Worker 구현

**백엔드 구현 및 비동기 분석 연동**

- Spring Boot 기반 이미지 등록, 분석 Job 생성·상태 관리와 결과 조회 기능 구현
- Spring Boot의 SQS 메시지 발행과 FastAPI AI Worker의 메시지 처리 로직을 연결해 비동기 분석 흐름 구현

## 트러블슈팅

### **01. 고해상도 이미지의 작은 결함 탐지 성능 개선**

#### **문제 상황**

원본 RGB 이미지는 평균 약 2000px의 고해상도였지만, AWS 기반 추론 환경의 메모리 사용량과 처리 비용을 고려해 입력 해상도를 낮춰야 했습니다.  
이 과정에서 **식생 침범과 파손처럼 작은 이상 영역의 픽셀 정보가 줄어 미탐이 증가했고, 전체 mask 성능과 클래스별 성능 편차 개선이 필요했습니다.**

#### **해결 과정**

##### **1. 입력 해상도 확대**

- 동일한 조건에서 입력 해상도 1024와 1280 비교
- mask mAP50-95가 0.42에서 0.43으로 향상된 1280 모델을 후속 실험의 기준으로 선정

##### **2. 식생 침범 라벨 정제**

- 전체 3,326장을 검수해 라벨 누락, 지나치게 작은 mask, 구분이 모호한 이미지 139장을 제외하고 3,187장으로 정리
- 작은 mask 제거 기준을 달리한 두 전처리 방식을 비교해 식생 침범 성능 개선 폭이 더 컸던 강화형 기준을 최종 적용

##### **3. fine-tuning 및 최종 모델 선정**

- 상위 후보 두 모델을 각각 10 epoch fine-tuning하고 낮은 학습률, 앞부분 11개 레이어 고정, Mosaic·MixUp·CutMix 비활성화 조건 적용
- 동일한 validation 기준에서 원본 모델과 epoch별 checkpoint의 전체 및 클래스별 성능을 비교해 성능 균형이 가장 좋았던 epoch 5 checkpoint를 최종 모델로 선정

#### **결과**

validation mask mAP50은 **0.68에서 0.71로**, 식생 침범 mask recall은 **0.41에서 0.57로** 상승해 작은 객체의 미탐 감소 효과를 확인했습니다.

| 핵심 지표 | 개선 전 | 개선 후 | 변화 |
| :---: | :---: | :---: | :---: |
| validation mask mAP50 | 0.68 | 0.71 | +0.03 |
| 식생 침범 mask recall | 0.41 | 0.57 | +0.16 |

#### **추가 실험**

성능 개선 가능성을 검토한 추가 실험과 적용에 제외한 사유는 아래와 같습니다.

- Slicing Aided Hyper Inference (SAHI) 기반 타일 추론 — 처리 시간이 약 3배 증가해 서비스 적용에서 제외
- 패널 어레이 기반 동적 crop 추론 — 이미지당 평균 13.6회의 반복 추론이 필요해 제외
- 오염(dusty) 클래스 개선 실험 — 별도 모델과 라벨 정제 모두 test 일반화 또는 전체 성능이 하락해 제외
- 파손(broken) 클래스 보강 fine-tuning — recall은 상승했지만 precision과 종합 성능이 하락해 제외


### **02. ONNX Runtime 원시 출력의 instance mask 복원**

#### **문제 상황**

Ultralytics 추론에서는 bounding box와 instance mask 후처리가 자동으로 제공되지만 raw ONNX 모델은 원시 tensor만 반환해 별도의 후처리가 필요했습니다. 초기 후처리에서 **letterbox의 축소 비율과 여백이 정확히 복원되지 않아 서비스 화면의 결함 박스와 세그멘테이션 영역이 실제 위치와 어긋나는 문제가 있었습니다.**

#### **해결 과정**

##### **1. ONNX 변환 및 출력 검증**

- 최종 RGB 모델을 raw FP32 ONNX로 변환하고 ONNX checker와 ONNX Runtime으로 모델 로딩 및 출력 구조 검증
- 동일한 validation 308장에서 PyTorch와 ONNX Runtime의 성능을 비교하고, 동일 이미지의 bounding box와 instance mask 정합성 검증

##### **2. instance mask 후처리 구현**

- letterbox와 정규화 전처리 후 confidence 필터링, 클래스별 NMS와 원본 좌표 복원 구현
- mask coefficient와 prototype을 결합하고 sigmoid, crop, resize를 적용해 객체별 instance mask 복원
- 같은 validation set에서 후처리 조건을 비교해 confidence 0.15, NMS IoU 0.40, mask threshold 0.30을 최종 적용

##### **3. AI Worker 적용 및 모델 검증**

- ONNX Runtime 추론과 후처리 모듈을 FastAPI AI Worker에 적용하고 모델 설정을 manifest로 관리
- SHA-256 검증과 smoke test로 모델 파일의 무결성과 정상 로딩 여부 확인

#### **결과**

동일한 validation 308장에서 PyTorch와 ONNX Runtime을 비교한 결과, **mask mAP50은 0.706 → 0.709, mAP50-95는 0.438 → 0.440으로 변환 후 성능이 유지**됐습니다.

| Runtime | Mask Precision | Mask Recall | mask mAP50 | mask mAP50-95 |
| :---: | :---: | :---: | :---: | :---: |
| PyTorch | 0.691 | 0.651 | 0.706 | 0.438 |
| ONNX Runtime | 0.680 | 0.649 | 0.709 | 0.440 |

PyTorch와 ONNX에서 매칭된 객체를 비교한 결과, **bounding box와 instance mask가 높은 수준으로 일치했으며 모델 아티팩트 크기를 PyTorch 대비 약 29% 감소**할 수 있었습니다.

| 비교 항목 | 이미지별 중앙값 범위 |
| :---: | :---: |
| bounding box IoU | 0.984–0.998 |
| mask IoU | 0.959–0.997 |


### **03. 조건부 상태 전이로 SQS 중복 추론 방지**

#### **문제 상황**

이미지 추론을 사용자 HTTP 요청과 분리하기 위해 SQS 기반 비동기 작업으로 구성했습니다. 그러나 **동일 메시지의 재전달이나 여러 Worker의 동시 수신으로 추론과 결과 저장이 중복 실행될 가능성이 있었습니다.**

#### **해결 과정**

##### **1. 메시지와 분석 대상 검증**

- jobId, imageId와 데이터베이스 조회 결과를 검증하고 QUEUED 상태의 Job만 처리 대상으로 구분
- RUNNING, SUCCEEDED, FAILED 상태는 추가 추론 대상에서 제외

##### **2. 조건부 상태 전환**

- QUEUED 상태인 Job만 RUNNING으로 변경하고 상태 전환에 성공한 Worker만 추론 수행
- 처리 결과에 따라 SUCCEEDED 또는 오류 정보를 포함한 FAILED 상태로 변경

##### **3. 메시지 삭제 시점 분리**

- Job 상태와 처리 결과를 데이터베이스에 반영한 뒤 SQS 메시지 삭제
- 정상 완료와 재시도가 필요한 오류를 구분해 메시지 삭제 정책 적용

#### **결과**

QUEUED에서 RUNNING으로의 **조건부 상태 전환에 성공한 하나의 Worker만 추론**하도록 하여 동일한 jobId가 반복 전달되거나 여러 Worker가 동시에 메시지를 수신해도 **중복 추론과 결과 저장을 방지**했습니다.


## 회고 및 배운점

다중 클래스 instance segmentation을 수행하면서 전체 평균 성능뿐 아니라 클래스별 성능 편차와 작은 객체의 미탐을 함께 보는 것이 중요하다는 점을 알게 되었습니다. 입력 해상도와 라벨 품질을 조정하고 SAHI 기반 sliced inference 같은 작은 객체 탐지 방법도 비교하면서, 성능 개선뿐 아니라 추론 비용과 서비스 적용 가능성까지 함께 고려했습니다.

ONNX 변환에서는 변환 전후의 성능과 출력 정합성을 실제 추론 환경에서 함께 검증했고, SQS 비동기 처리에서는 Job 상태 전이와 메시지 삭제 시점을 함께 설계했습니다. 이를 통해 모델을 서비스에 적용할 때는 모델 성능뿐 아니라 추론 환경과 상태 관리까지 함께 고려해야 한다는 점을 배웠습니다.
