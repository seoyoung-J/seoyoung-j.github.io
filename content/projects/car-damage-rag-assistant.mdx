## 프로젝트 개요
차량 손상 모델의 탐지 결과만으로는 사용자가 손상 부위를 확인한 이후 무엇을 추가로 촬영하고, 수리 전 어떤 항목을 점검하며, 보험 제출을 위해 어떤 자료를 준비해야 하는지 판단하기 어렵습니다. 또한 운행 가능 여부나 수리비처럼 사진만으로 확정하기 어려운 질문에는 신중한 안내가 필요합니다.

이 프로젝트는 차량 이미지에서 손상 유형과 위치를 분석하고, 분석 결과와 질문 목적에 맞는 대응 가이드를 제공하는 시스템입니다. 손상 확인 이후 필요한 추가 촬영, 수리 전 점검과 보험 준비 과정을 안내하며, 근거가 부족하거나 안전 판단이 필요한 질문은 제한된 안내로 전환하도록 구성했습니다. 

## 핵심 시스템 흐름

1. 사용자가 Streamlit에서 차량 이미지를 업로드합니다.
2. YOLOv26n-seg가 6개 손상 유형을 탐지·분할하고 bounding box, instance mask와 confidence를 추출합니다.
3. 탐지 결과를 위치와 추가 확인 항목으로 후처리해 analysis_id 기준 JSON으로 저장합니다.
4. 사용자가 탐지 결과를 확인하고 추가 촬영, 수리 전 점검과 보험 준비에 관한 질문을 입력합니다.
5. LangGraph가 탐지 결과와 근거 문서를 연결해 답변 또는 Fallback 안내를 반환합니다.

## LangGraph 기반 RAG 흐름

1. 질문의 지원 범위와 Intent를 분류하고 확정하기 어려운 질문은 Fallback으로 분기합니다.
2. analysis_id로 탐지 결과를 조회하고 질문, Intent, 손상 유형과 위치를 반영한 복수 query를 생성합니다.
3. FAISS 검색 결과를 병합한 뒤 동일한 chunk를 제거하고 문서 우선순위에 따라 재정렬합니다.
4. source당 최대 2개, 최종 최대 5개 chunk로 근거를 구성합니다.
5. 근거가 충분하면 Ollama로 답변을 생성하고, 부족하면 Fallback 안내를 반환합니다.

## 트러블슈팅

### **01. 탐지 결과를 반영한 검색 파이프라인과 평가 흐름 개선**

#### **문제 상황**

초기 RAG 검색은 사용자의 질문만 사용해 이미지에서 탐지된 손상 유형과 위치를 검색에 반영하지 못했습니다. 이후 복수 query를 적용했지만 동일한 chunk와 source가 반복되면서 검색 결과의 중복과 편중이 발생했습니다.

#### **해결 과정**

##### **1. 검색 구성 비교 및 선정**

- 차량 손상과 후속 대응 정보를 21개 Markdown 문서로 구성하고 청킹 전략 3종과 E5 임베딩 모델 2종 비교
- 검색 품질과 지연시간을 기준으로 236개 chunk와 multilingual-e5-small 선정

##### **2. 탐지 결과 기반 검색 정제**

- analysis_id로 조회한 손상 유형 및 위치와 질문 Intent를 결합해 복수 retrieval query 생성
- 검색 결과 병합 후 동일한 chunk를 제거하고 Intent·손상 유형·문서 우선순위에 따라 재정렬
- source당 최대 2개, 최종 최대 5개 chunk로 제한해 중복과 특정 문서 편중 완화

##### **3. 서비스와 평가 흐름 일치**

- 실제 서비스의 탐지 결과 조회, 복수 query, 중복 제거와 재정렬 로직을 평가에서도 동일하게 사용
- 23개 회귀 질문을 대상으로 문서 적중률, 검색 순위와 지연시간 검증

 #### **결과**

Section Hit Rate를 21.73%p 높였으며, 23개 회귀 질문 모두에서 기대 문서가 상위 5개 검색 결과 안에 포함됐습니다. 평균 검색 지연시간은 122.35ms, P95는 143.99ms로 확인했습니다.

| 핵심 지표 | 최종 결과 |
| :---: | :---: |
| Document Hit Rate@5 | 1.00 |
| Mean Reciprocal Rank (MRR) | 0.84 |
| Mean Average Precision (MAP) | 0.57 |

Document Hit Rate@5 1.0000은 모든 질문에서 기대 문서가 상위 5개 안에 최소 1개 포함됐다는 의미입니다. 기대 문서가 처음 등장한 순위는 Mean Reciprocal Rank (MRR)로, 여러 관련 문서가 검색 결과 상위에 배치된 정도는 Mean Average Precision (MAP)으로 함께 평가했습니다. 해당 수치는 기존 오류 문항을 포함한 회귀 평가 결과입니다.


### **02. 유사 질문의 Intent 혼동과 안전 답변 제어**

#### **문제 상황**

차량 손상 질문은 표현이 비슷해도 추가 촬영, 보험 제출, 수리 전 점검과 안전 확인처럼 목적이 다릅니다. 초기에는 보험 제출 질문이 일반 촬영 질문으로 분류되거나, 운행 가능 여부처럼 사진만으로 확정하기 어려운 질문이 일반 답변 경로로 전달되는 문제가 있었습니다.

#### **해결 과정**

##### **1. Intent 분류 기준 보완**

- 질문 목적을 손상 설명, 심각도 해석, 추가 촬영, 보험 제출 자료, 보험 판단 확인 항목, 수리 전 점검과 Fallback의 7개 Intent로 구분
- 보험 제출과 일반 촬영 질문의 구분 기준을 추가하고, 안전·수리비·보험 결과처럼 확정하기 어려운 질문을 우선 검사하도록 분류 순서 조정

##### **2. LangGraph 답변 경로 분리**

- 질문 검증, 탐지 결과 조회, 문서 검색, 근거 판단, 답변 생성과 Fallback을 개별 node로 구성
- 지원 질문은 검색과 답변 생성으로 연결하고, 안전 판단이나 확정이 어려운 질문은 conditional edge를 통해 Fallback으로 분기

##### **3. 회귀 테스트 적용**

- 기존에 혼동이 발생한 추가 촬영·보험 제출·안전 질문을 회귀 테스트로 구성
- 분류 규칙 수정 후 각 질문이 의도한 Intent와 Fallback 경로로 전달되는지 검증

#### **결과**

추가 촬영과 보험 제출 질문을 구분하고, 사진만으로 확정하기 어려운 질문은 일반 답변 생성 경로에서 제외했습니다. 해당 결과는 기존 오류 문항을 대상으로 수정 사항의 재발 여부를 확인한 회귀 테스트 결과입니다.

| 검증 항목 | 결과 |
| :---: | :---: |
| Intent 분기 회귀 테스트 | 35/35 |
| Safety Fallback 경로 검증 | 7/7 |

## 주요 성과

### 1. **차량 손상 탐지 및 결과 구조화**

YOLOv26n-seg로 6개 차량 손상 유형을 탐지·분할하고, 결과를 `analysis_id` 기준 JSON으로 저장·조회해 Streamlit에서 시각화하는 분석 흐름 구현

### 2. **탐지 결과 기반 RAG 검색 개선**

21개 문서를 236개 chunk로 구성하고 탐지 결과 기반 복수 query와 검색 결과 정제를 적용해 23개 회귀 질문 모두에서 기대 문서를 상위 5개 내에 포함, Document Hit Rate@5 1.00 및 Mean Reciprocal Rank (MRR) 0.84 기록

### 3. **LangGraph 기반 답변 경로 제어**

7개 Intent와 Fallback 분기 구조를 구성해 Intent 분기 35건과 Safety Fallback 7건의 회귀 테스트 통과

## 향후 고도화 방향

현재는 차량 손상 탐지 결과와 문서 검색을 연결하는 로컬 프로토타입으로 구현했습니다. 향후에는 독립 질문 세트를 활용해 검색과 Intent 분류의 일반화 성능을 검증하고, reranker 적용을 통해 검색 결과의 우선순위를 정교화할 수 있습니다. 또한 영속 저장소와 다중 사용자 요청 처리 구조를 추가해 실제 서비스 형태로 확장할 수 있습니다. 

## 회고 및 배운점

차량 손상 탐지 결과만 제공하는 것으로는 사용자가 이후에 어떤 사진을 추가로 촬영하고 무엇을 점검해야 하는지 충분히 안내하기 어렵다는 점을 확인했습니다. 이미지 분석 결과를 검색 query에 반영하고, 질문 목적에 따라 서로 다른 문서를 선택해야 탐지 결과와 후속 가이드를 자연스럽게 연결할 수 있었습니다.

또한 RAG 검색은 기대 문서가 포함됐는지만 확인하는 것이 아니라 문서의 순위, 불필요한 결과와 검색 지연시간을 함께 평가해야 했습니다. LangGraph로 검색 근거와 질문 범위에 따라 답변 경로를 분리하면서, 답변 생성 성능뿐 아니라 답변하지 않아야 하는 상황을 제어하는 구조도 중요하다는 점을 배웠습니다.
